# Decisions log

Choices made while building Phase 1 unattended, newest at the bottom.

| # | Decision | Why |
|---|----------|-----|
| 1 | The project lives in `software-factory/` instead of the repo root. | This repo is also the owner's GitHub profile (root `README.md`) and a GitHub Pages site (`index.html`, `pages.yml`). Writing the factory to the root would replace the profile README. The CI workflow has to live at `.github/workflows/factory-ci.yml` and uses `working-directory: software-factory`. |
| 2 | Docker check: the daemon was not running at first. `dockerd` started fine, so **Testcontainers (real PostgreSQL 16) is used for every DB test**, not H2. | The brief asked to check and note the result. Real Postgres means `FOR UPDATE SKIP LOCKED` and partial unique indexes are tested for real. |
| 3 | Docker Hub returned `429 Too Many Requests` in this sandbox. Images were pulled from `mirror.gcr.io` and tagged locally (`postgres:16-alpine`, `testcontainers/ryuk:0.12.0`). | Only affects this build machine. GitHub Actions runners pull from Docker Hub normally, so no workaround is committed. |
| 4 | Spring Boot 3.5.16 (latest 3.5.x on Maven Central at build time). Testcontainers version is managed by the Boot BOM. | Brief fixed the 3.5.x line. |
| 5 | Persistence uses Spring `JdbcClient` and hand-written SQL, not JPA. | The job claim (`FOR UPDATE SKIP LOCKED`) and the guarded state updates (`UPDATE ... WHERE state = ?`) are clearer and more predictable as explicit SQL. Fewer moving parts. |
| 6 | CI runs on every push and pull request (no path filter), as the brief says. | Literal reading of "every push and PR". |
| 7 | One job row per ticket for its whole life. Waiting (retry backoff, approval polling) reschedules the same row with a later `run_after`. | Keeps "one live job per ticket" enforceable with one partial unique index, and no worker thread is tied up while waiting. |
| 8 | The pipeline resumes from the persisted ticket state on every run, instead of keeping progress in memory. | A crash, a lease expiry or a retry continues where it stopped. Opening a PR is skipped if `pr_number` is already set, so a retry can't open a duplicate PR. |
| 9 | `max-retries` (default 3) is one counter per ticket, shared by failed steps and failed checks. | One easy-to-understand cap on total rework. Retries use linear backoff (`retry-backoff × n`). |
| 10 | Guardrail breaches (cost, turns, timeout) fail the ticket immediately and are never retried. | A retry would spend more of the money or time the limit exists to protect. |
| 11 | Cost and turns are checked **after** each agent run, against the ticket's running totals. The remaining budget is passed into `AgentRequest` so a real agent can stop early. | The fake (and Claude Code) report usage at the end of a run, so the run that crosses the line is recorded, then the ticket fails. A real agent given `--max-turns` should rarely overshoot. |
| 12 | The hard timeout does not count time spent in AWAITING_APPROVAL. | It limits machine work. A PR waiting a day for a human should not be marked FAILED. |
| 13 | AWAITING_APPROVAL → CODING ("changes requested") is not allowed in Phase 1. | That belongs with the reviewer agent and real GitHub reviews (Phase 2). Adding it later is a one-line table change plus a test update. |
| 14 | Success rate = DONE / (DONE + FAILED). CANCELLED is left out. Avg cost covers finished tickets; total cost covers all tickets. | Cancelling is a human choice, not a factory failure. Written on the stats page as well. |
| 15 | Fakes can be scripted per ticket with `fake-*:` lines in the issue body, in addition to config and test overrides. | One running demo can show every path (retry, guardrail, pending approval) without restarts. Documented in README. |
| 16 | The fake GitHub is in-memory. After a restart it has forgotten its PRs, so a ticket left in AWAITING_APPROVAL across a restart reads its PR as CLOSED and becomes CANCELLED. | Acceptable for a fake; it doesn't affect tests or the first-run demo. The real client won't have this problem. |
| 17 | The demo seeds only **finished** tickets (12 DONE, 4 FAILED, 2 CANCELLED), written with backdated timestamps. Each path is validated against `TicketStateMachine` first. The in-progress tickets come from 4 live fake issues that go through the real pipeline. | A seeded "in progress" ticket would have no job and would sit stuck forever. Live issues show the real thing. Total on first run: 22 tickets. |
| 18 | The dashboard POST actions (cancel, approve) and `/api/fake/*` have no authentication. | Phase 1 is a local demo. Listed as not built in README and DESIGN. |
| 19 | `insertIfAbsent` uses `INSERT ... SELECT ... WHERE NOT EXISTS ... ON CONFLICT DO NOTHING`. | Plain `ON CONFLICT` used up a sequence value on every poll, which made ticket ids jump (seen during the live demo run: the 23rd ticket got id 63). `ON CONFLICT` stays as the safety net for races. |
| 20 | **`docker compose build` could not be fully verified here.** The Maven stage inside the build container can't reach Maven Central through this sandbox's TLS-intercepting proxy. I verified the runtime instead: the same `eclipse-temurin:21-jre` stage built from the locally built jar, then `docker compose up --no-build`. The app came up healthy against the compose Postgres and served the demo dashboard. | A limit of this environment, not of the Dockerfile, which is a standard two-stage Maven build. On a normal machine `docker compose up --build` should work, but I did not see it complete. |
| 21 | Tests have no H2 fallback. They need Docker (Testcontainers). | Docker was available here, and GitHub runners have it. An H2 fallback would mean keeping a second SQL dialect for the queue, and it would test something other than what runs in production. |
| 22 | (M0) Heartbeat every `lease-timeout / 3` and keep `lease-timeout` at 10 minutes, rather than raising the lease above the hard timeout. | A long lease would also make recovery after a real worker crash take that long. With a heartbeat, a dead worker's ticket is picked up within one lease, and a live worker can run as long as the guardrails allow. |
| 23 | (M0) The lease identity includes `attempts`, not just `locked_by`. | Worker ids can repeat (tests, or one worker reclaiming its own expired job). `attempts` goes up on every claim, so an older claim can never pass for the current one. |
| 24 | (M0) A transient heartbeat error (DB unreachable) does not mark the lease lost; the heartbeat keeps retrying. Only a renewal that the database rejects means "lost". | A brief DB blip shouldn't abandon a 15-minute agent run. If the DB stays away longer than the lease, the reaper hands the job on, and the first successful renewal then reports the loss. |
| 25 | (M0) While waiting for the agent, the pipeline wakes every 250 ms to check the hard timeout, the lease, and whether the ticket was cancelled. | This is the Java side of cancellation (finding 5): a cancelled ticket stops waiting within a fraction of a second. Killing the real agent process stays in M5; today `future.cancel(true)` only interrupts the thread. |
| 26 | (M0) `factory.integrations=real` fails startup with an explicit message until M2–M5 exist. The check is a static `BeanFactoryPostProcessor`. | My first version was an ordinary bean. Starting the real app showed `GitHubPoller` failing first with "required a bean of type GitHubClient". A bean-factory post-processor runs before any regular bean is created, so the clear message always wins (checked with `java -jar` and in `IntegrationModeTest`). |
| 27 | (M0) `TwoInstancesTest` starts the second app instance with `SpringApplicationBuilder`, passing the shared database as command-line args. | Builder `.properties(...)` are defaults and lose to `application.yml`, so the second instance silently tried `localhost:5432` (seen while writing the test). |
| 28 | (M1) **A ticket is one attempt** (an `attempt` column on `tickets`), instead of the separate `attempts` table the plan sketched. | Everything the pipeline tracks (state, history, usage, sandbox, branch, PR, job) is per run, so the existing table already *is* the attempt. An issue is just `(repo, issue_number)`. Snapshotting title and body per attempt is a feature: a retry after someone improves the issue should see the new text. This kept the state machine, queue and pipeline untouched. |
| 29 | (M1) A new attempt needs a **new trigger** (label re-applied after the last attempt's trigger), not just "the last one finished". | Otherwise an issue that fails and keeps its label would be retried on every poll, burning money. Re-labeling is an explicit human decision. The real client (M2) reads the trigger time from the issue's `labeled` events. |
| 30 | (M1) Re-labeling while an attempt runs doesn't start a parallel one; the newer trigger is honored after the running attempt finishes. | One unfinished attempt per issue keeps branches and PRs unambiguous. Treating the re-label as "run again afterwards" is the least surprising reading. Covered by `AttemptsTest`. |
| 31 | (M1) Closing or unlabeling an issue cancels its attempt only before a PR exists. | Merging a PR with "Closes #N" closes the issue a moment before the pipeline sees the approval. Cancelling then would record a successful ticket as CANCELLED. Covered by `GitHubPollerTest.closingTheIssueAfterThePrIsOpenDoesNotCancel`. |
| 32 | (M1) The poller lists *all* open labeled issues each time (paged inside the client) instead of an incremental `since` cursor. | Reconciliation needs the full set to notice issues that disappeared. The cost is rate limit; M2 will use conditional requests (ETag) to make unchanged pages free. |
| 33 | (M1) The factory doesn't remove the trigger label when a ticket finishes. | Not needed for correctness (decision 29), and it means writing to GitHub issues. M2 can add outcome labels (`factory:done`, `factory:failed`) as a UX touch. |
| 34 | (M1) The fake agent now stays within `maxTurns` unless an issue's `fake-agent-turns` directive says otherwise. | The contract requires a real agent to honor its turn limit. The directive still simulates an agent that overshoots, which is what the turn guardrail test needs. |
| 35 | (M1) Contract suites are top-level test classes, one per fake (`Fake*ContractTest`). | First version used JUnit `@Nested` classes, and Surefire silently ran 0 of them (it excludes inner classes by default). Caught because the report said "Tests run: 0". |
| 36 | (M2) The client supports **both** GitHub App and token auth, picked by which env vars are set. | The App-or-token decision is still open. Supporting both cost one small class and unblocked M2. The App stays the recommendation: narrow permissions, one-hour tokens, and actions show as the App rather than a person. |
| 37 | (M2) Tested against a home-made **GitHub API simulator** (JDK `HttpServer`) instead of WireMock as the plan said. | The contract needs state (create an issue, then list it; open a PR, then find it), which is awkward in WireMock stubs, and the simulator also covers faults, ETags and paging. One less dependency. The trade-off: the simulator is my reading of GitHub's documented behavior, so the live nightly test is what confirms it against the real thing. |
| 38 | (M2) Only issues labeled by someone with **write** (configurable) are accepted, judged by the *latest* labeling. | Anyone can open an issue and write anything in it; the label is the gate. Checking the latest labeler stops "remove + re-add by a stranger" from slipping through. A side effect: a stranger re-labeling an issue makes it disappear from the listing, which cancels a running attempt that has no PR yet. Anyone with triage rights could cancel by removing the label anyway. |
| 39 | (M2) Rate limits **pause** the ticket until the reset instead of counting as a failed step. | The ticket did nothing wrong. Counting it would fail healthy tickets during a busy hour (an hour-long primary limit easily outlasts 3 retries with 2 s backoff). |
| 40 | (M2) "Changes requested" keeps the PR PENDING for now. | Sending review comments back to CODING needs the AWAITING_APPROVAL → CODING edge and the reviewer loop (finding 13), planned for later. Until then a human resolves it on GitHub. |
| 41 | (M2) Live tests are a JUnit tag excluded from the normal build, run by a separate workflow that skips cleanly when not configured. | A normal `mvn verify` and every PR stay fast and free of secrets. The live job is a no-op until the repo variable and token secret exist. |
| 42 | (M2) The live test approves PRs by **merging** them. | GitHub doesn't let a token approve its own PR, and a second identity is extra setup. The client reports merged PRs as APPROVED, so this still exercises the same path. It does mean small files land in the test repo's default branch, which is why it must be a throwaway repo. |
| 43 | (M3) Code goes into and out of the sandbox as **git bundles**, and the **host** fetches and pushes. | The sandbox then needs no network and no token, the strongest isolation available. A bundle is one file, so the transfer is simple and complete (full history of the branch). Trade-off: big repos make big bundles; shallow bundles can come later if needed. |
| 44 | (M3) The sandbox has **no network at all**; the allowlisted egress proxy moves to M5. | Nothing in M3 needs network inside the sandbox. Only the agent (M5) needs one destination, the model API, so the proxy is designed and tested together with the thing that uses it. |
| 45 | (M3) `/workspace` is **tmpfs**, not a Docker volume. | With all capabilities dropped, nothing in the container can `chown` a root-owned volume, and the sandbox user can't write to it. tmpfs can be mounted owned by uid 1000, is size-limited, and disappears with the container (no leftover volumes). Cost: it counts against the memory limit (4 GB default, workspace 2 GB), and a container restart loses the workspace, so a stopped sandbox is replaced (the ticket redoes its work). |
| 46 | (M3) Files are streamed through `docker exec` (`head -c <size>` in, `cat` out), not Docker's archive API. | The archive API refuses to write into a container with a read-only root filesystem, even into a tmpfs, and its reads don't see tmpfs. Also: docker-java never closes exec stdin, so `cat > file` would wait forever; `head -c <exact size>` stops by itself (found when the first version hung). |
| 47 | (M3) docker-java 3.4.2 (same as Testcontainers), with commons-compress, commons-io and Guava pinned to current versions. | docker-java brings commons-compress 1.21 and Guava 19, which have published CVEs. The newer commons-compress then needed a newer commons-io (found by a `NoSuchMethodError` in the first test run). |
| 48 | (M3) The Docker socket is mounted into the app container for real mode, with a warning in `docker-compose.yml`. | It's the standard way for a containerized app to start sibling containers. It is root-equivalent on the host, so the factory must run on a machine dedicated to it. Rootless Docker or a remote Docker host would reduce this; noted for the pilot. |
| 49 | (M3) The janitor runs in every mode and only removes sandboxes of finished or missing tickets. | Running tickets may be resumed by another worker after lease recovery and should find their sandbox. Missing tickets cover a wiped database. |
